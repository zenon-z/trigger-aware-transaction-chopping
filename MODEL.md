# MODEL.md: Modeling and Implementation Decisions

Design log of the static analysis (`chop.py`) and the runtime harness (`runtime/`): one entry per decision, with the choice, the reason and where it lives in the code. Code comments refer to these entries by number (F6, R15, ...). Dates refer to 2026 and record when a decision was made during development; TPC-C clause numbers refer to rev. 5.11. Entries about experiments that are not in the paper (full TPC-C mix, coarsening chain, district layout, local runs) document the harness and are kept for completeness. **Terminology:** "CPR" (consistency preservation rule) is the development name for a trigger, B-inc and B-rec are the incremental and recomputing triggers, and an "arm" is a measured variant.

## Formalism and conflicts

| # | Decision | Choice | Reason | Where |
|---|---|---|---|---|
| F1 | Template formalism | Operations `R`, `W`, `U` over relations with attribute sets, following Vandevoort, Ketsman, Koch, Neven (PVLDB 2021, ICDT 2022) | The formalism reviewers know | `op(oid, kind, rel, *attrs)` |
| F2 | Data items | Attribute-level cells (relation, attribute, tuple) | Avoids spurious conflicts between operations on different attributes of the same row; matches Definition 4 | `op(..., *attrs)`, `conf_op` |
| F3 | Variable equality | Conservative: tuple identity is ignored, so any two operations on the same relation and attribute may hit the same tuple | Safe default; Proposition 1 depends on it | `conf_op` (compares `rel`, `attrs` only) |
| F4 | Conflict | Two operations conflict iff they share a cell, at least one writes it, and they are not both commutative updates | Definition 4 extended by commutativity | `conf_op`, `conf` |
| F5 | Commutative updates | A `U` is commutative iff it is an increment `x += δ` whose new value is not read or returned. δ may depend on earlier reads, since those reads conflict on their own | Shasha defines C-edges as non-commutativity, with syntactic conflict as the fallback and inventory additions as the commutative example (TODS 1995, Section 3, p. 330); IC3 drops C-edges between commutative operations | `op(..., comm=True)`; `validate` rejects `comm` on non-`U` |
| F6 | Execution model | Pieces run under **strict 2PL on rows**: READ COMMITTED plus explicit row locks held until the piece commits. UPDATEs lock their row, and the B-rec trigger's read takes `FOR SHARE`. Before the statement that fires a CPR, the client locks the rows that CPR writes, here the warehouse row (`FOR NO KEY UPDATE`), in the same piece. The rule is the same for both triggers (R3). This is not an extra operation: it acquires a lock the CPR takes anyway, only earlier, and order within a piece doesn't affect the analysis. In B-rec, with the warehouse row locked first, the share locks cannot deadlock. A `BEFORE` trigger cannot do this, because Postgres locks the district row while fetching it for the trigger. **Reads of cells that are never written take no lock (changed Oct 14; before: `FOR KEY SHARE`).** No write can conflict with them, so no lock is needed for serializability. The `FOR KEY SHARE` they took before never protected them either: it does not conflict with `FOR NO KEY UPDATE`, so it would not have stopped a concurrent overwrite of `w_name`; it only blocks deletes and key changes, which TPC-C never does. Correctness rested on the cells never being written all along; that workload dependence is stated here, where the read rule is. Dropping the lock removes a Postgres cost: every concurrent share holder of the warehouse row became a member of the multixact Postgres builds on each update of that row (about 130 members per unchopped Payment at 1 warehouse × 32 clients, zero without the lock; local measurement). Reads of written cells keep their locks (the B-rec trigger's `d_ytd`, OrderStatus' balance, carrier and order-line reads: `FOR SHARE`; Delivery's oldest new order: `FOR UPDATE`). The local campaign of Oct 7–9 ran under the old rule; the server campaign runs under this one. Arm suffix `@keyshare` restores the old rule for comparison. Deadlocks are retried per piece (Shasha's execution rule 3). **What the paper may claim:** our protocol has one lock order (warehouse before district, in every piece), so no deadlock arises from lock ordering. Postgres can still report rare deadlocks inside its own row-lock queue on the single hot warehouse row; retry absorbs them. Observed in the local campaign (Oct 7–9): one such event in about 3,400 Payment-only runs (Payment only, stock layout; 13 errors from that one event, each aborting and retrying one piece). The log shows four Payments in the same call (warehouse pre-lock, then district update); the only row all four touch is the warehouse row; three are queued for it, the head waits for the holder, and the holder waits for the transaction of a Payment queued behind that same row. Our lock order cannot create that last edge, so the cycle closes inside Postgres' row locking, not through the protocol's lock order. Which internal path closes it is not visible in the log and is not claimed. The full mix's deadlocks (72 in 800 runs) are NewOrders updating stock rows in opposite order (the last item stays last, R16) and Delivery/OrderStatus on order and customer rows, as expected. Commutativity is used only by the analysis: concurrent increments of the same row wait for each other | Shasha's Fact † (2PL gives an acyclic serialization graph of the pieces) applies as written. Serializable here because every access is a key lookup or one of two range reads, all districts of a warehouse (B-rec trigger) and the customers with one last name in a district (Payment's `pc` by name, R12); both cover rows that are never inserted or deleted, and the columns `pc` matches on are never written. In the full mix, Order, NewOrder and OrderLine rows are inserted and deleted while other templates search them; district-level table locks (R13) act as predicate locks for those searches, so 2PL on rows plus these locks is again serializable. Postgres locks rows, not cells; locking more coarsely than the analysis stays 2PL and only adds waits (e.g. Payment's `c_balance` and `c_ytd_payment` updates share a customer row). `--cc ssi` (SERIALIZABLE) is kept as an alternative; SSI's extra read-write aborts would add noise to the retry count | `runtime/payment.py` (`CC`, `OP_SQL_2PL`, `prologue_for`), `schema.sql` (`cpr_wytd_rec_lock`, `consistency_violations`) |
| F7 | `U` is primitive | A `U` is one access and is never split into `R` and `W` across pieces | Shasha's Enclosing Conflict Assumption (Shasha et al., TODS 1995, p. 335, before Lemma 3, including the warning not to chop increments into their reads and writes). Theorems 4 and 5 (FineChop finds the finest correct chopping) rely on it | `kind="U"` |
| F8 | Terminal output | Values displayed on the terminal count as reads | Displayed values are returned to the client | `comm=False` on `pa5` (`c_balance`), `no8a`/`no8b` (`s_quantity`) |
| F9 | Predicate reads and inserts | Modeled as accesses to a pseudo-attribute standing for the whole relation (`o_row`, `no_row`, `ol_row`, `h_row`) | Covers phantoms conservatively | TPC-C templates |

## Instances, order and rollbacks

| # | Decision | Choice | Reason | Where |
|---|---|---|---|---|
| I1 | Instances | Every template that can run concurrently with itself takes part with two instances; all other transactions stay unchopped in a private chopping | Shasha adds the second copy exactly in that case | `conflict_components` (`for i in (1, 2)`) |
| I2 | Data flow | `uses` lists the operations whose values an operation consumes. Producer → user becomes a dependency-graph edge, like a conflict edge | Shasha's dependency graph only orders conflicting operations, which is valid only if no value flows between pieces | `op(..., uses=[...])`, `deps`, `dependency_graph` |
| I3 | Spec-required order | `after` lists operations that must precede for reasons other than data flow | Encodes ordering rules from the spec (see S4) | `op(..., after=[...])`, `deps` |
| I4 | Dependency cycles | Pieces on a dependency cycle are merged; pieces run in a topological order | Makes the piece order executable by construction | `fine_chop` (SCC merge, `lexicographical_topological_sort`) |
| I5 | Rollback hoisting | Before the analysis, each rollback point moves as early as it can. It moves past an operation only if it does not depend on it (`uses`/`after`) and their CPR projections do not conflict. Hoisting is computed per scenario, and every move is printed | Shasha's advice to move rollbacks early, applied as a checked program transformation | `hoist_rollback`; `chop.py -v` prints the moves |
| I6 | Rollback-safety | Shasha's strict rule on the rewritten template: the first piece contains the rollback points, every write before them, and every dependency-graph ancestor | Shasha's definition; the proofs are written against it | `fine_chop` (rollback branch), `tpl(..., rollback=[...])` |
| I7 | Hoist blocked by a CPR | Flagged separately: the merge then comes (at least partly) from rollback-safety, not from a conflict | Keeps Proposition 2 attribution clean | `chop_config` (`blocked`), `†` in the table |
| I8 | Initial chopping | The finest rollback-safe chopping; FineChop merges from there | What FineChop expects | `fine_chop` |

## CPR assumptions (the paper must state these too)

| # | Decision | Choice | Reason | Where |
|---|---|---|---|---|
| C1 | Triggered operations | A CPR fires on a write to a source cell and runs a set of triggered operations (reads and writes), each with its own commutativity flag | Definition 2; derived values need reads | `cpr(rel, attr, *triggered)` |
| C2 | Labelled instances | Every operation, original or triggered, is a distinct labelled instance | Assumption 1 (freshness) fails if operations are identified by kind and item only | `projection` (triggered ids `trigger>op`) |
| C3 | Placement and order | Triggered operations belong to their trigger's piece (Definition 11) and inherit their trigger's position: x ≺ᵢ* y iff trigger(x) ≺ᵢ trigger(y), or x is the trigger of y (lifted Definitions 3 and 9: the same order for the multi-model transaction and its closure) | Synchronous triggers run right after their triggering statement. Ordering a triggered operation only after its trigger would break Lemma `dg` | `projection`; `dependency_graph` (original positions, conflicts on projections) |
| C4 | Trigger guard | A triggered write never triggers another CPR. Two-way sync is two one-directional CPRs | Keeps Definition 9 a partial order and Assumption 1 intact | `projection` (no recursion) |
| C5 | No abort | CPRs never abort | Otherwise the trigger becomes a rollback point and the rollback part of Lemma `pc` changes | Not implemented: there is no `may_abort` field |
| C6 | Static `cprs` | The CPR relation is known statically at the template level | Prerequisite for any static analysis | `*_SCENARIOS` dicts |

## Runtime CPR implementation (accepted)

| # | Decision | Choice | Reason / framing |
|---|---|---|---|
| R1 | Where the models live | Both models are tables in one Postgres database; the CPR is a trigger | The analysis is about atomic units and cells, not about where models live. **Limitation:** the runtime measures lock behaviour, not cross-system synchronization |
| R2 | `w_ytd` maintained by a CPR | Payment's own `w_ytd` update is removed; the CPR maintains consistency condition 1 | **B-inc is "TPC-C as specified":** `w_ytd += amount`, only executed by a trigger. **B-rec** is an alternative implementation of the same invariant |
| R3 | Lock order | **Same rule for every CPR:** before a statement that fires a CPR, the client locks every row that CPR writes (here the warehouse row, `FOR NO KEY UPDATE`), in the same piece. Derived from the CPR definitions (`prologue_for` in `runtime/payment.py`). The lock statement is sent **in the same call as the triggering statement** (one round trip). This is part of the rule, not tuning: in a real system the CPR takes its lock inside the trigger, within the triggering statement, so there is no round trip between taking the lock and the update. A separate statement would be an artifact of the client doing the trigger's locking and would inflate the hold time of the hottest lock. In B-rec the rule prevents deadlocks; in B-inc it takes the same lock a moment earlier. | **Framing:** the lock order is part of the CPR's specification. A CPR declares the cells it writes (static, C6), and the executor takes those locks before running the trigger's source statement. A self-contained trigger cannot do this in Postgres: a row-level `BEFORE` trigger runs after the district row is locked, and a statement-level one doesn't know the warehouse. Without it, B-rec deadlocks often and mixes aborts into the comparison |
| R4 | Analysis vs. runtime granularity | The analysis ignores tuple identity (conservative, F3); Postgres locks rows, not cells | Two sentences in the paper. Coarser analysis can only merge more, so the executed chopping is always safe. In the other direction, row locks add waits the analysis doesn't predict (the customer row shared by `c_balance` and `c_ytd_payment`) |
| R6 | Executed chopping | FineChop's finest chopping, as produced, including the conflict-free read pieces `{pa2}`, `{pa4}` and `{pc}` | It's what the paper's algorithm produces, so it's what the evaluation measures. **Discussion sentence:** an executor would merge pieces that conflict with nothing (Shasha recommends not chopping conflict-free pieces), and coarsening a correct chopping is always correct (Shasha's Lemma 2). This would lower chopping's cost at low contention for both triggers alike, so the B-inc vs. B-rec comparison is unaffected |
| R7 | Static table vs. runtime workload | The static table uses the full TPC-C mix. The runtime has two workloads: Payment only (`payment.py`, the main experiment) and the full mix (`mix.py`, decided Oct 7: a robustness check that Payment's effect survives in a realistic workload) | Payment's chopping is identical in both (checked with `chop.py`). **Setup sentence:** state this once, since a reader comparing the table with the runtime pieces will notice |
| R8 | Mechanism metric | Warehouse-lock hold time per Payment: from the moment the pre-lock is granted to the commit of the piece holding it, reported as median and p95 per run (`wlock_hold_p50_ms`, `wlock_hold_p95_ms`). The server notes the time right after the lock statement and returns the elapsed time at the end of the same call; the client adds the time from that response to the commit acknowledgement. No extra round trip, lock waits excluded | It measures what the analysis predicts (how long the hot lock is held) and, unlike throughput gains, doesn't collapse under overload. **Paper structure:** hold time is the mechanism evidence, throughput its consequence. Predicted order: B-inc chopped (one statement) < B-rec chopped (three statements) < unchopped (almost the whole Payment) |
| R9 | Gains under overload | The result is reported for the range where the system isn't saturated. At 1 warehouse and 64 clients both baselines collapse (p95 in seconds), and the gains converge | A ratio of two collapsing numbers says nothing about the mechanism. Describe 64 clients at 1 warehouse as overload where every arm converges |
| R10 | Coarsening order (server `coarsen` stage) | From FineChop's finest chopping down to one piece, in the **reverse of the order in which chopping adds value**. **Step 1:** conflict-free reads first: `{pa2}`, `{pa4}` and `{pc}` merged with each other, then into the contended piece. **Step 2:** free hot increments into the contended piece, coldest cell first by rows per warehouse: `pa6` (customer, 30,000 per warehouse) before `pa3` (`d_ytd` 10 and `w_ytd` 1 per warehouse). **Last step:** one piece = the unchopped transaction. B-inc: 6 → 5 → 4 → 3 → 2 → 1; B-rec: 5 → 4 → 3 → 2 → 1 (`pa3` is already contended there). After each merge the dependency graph is checked to be acyclic and the pieces re-sorted | The reads hold no contended lock, so merging them removes cost without removing benefit (Shasha's rule of thumb: don't chop pieces involved in no conflicts); this first step is the one an executor would make anyway. Ordering the increments coldest first makes the final steps the ones that give up the hottest locks, so the throughput drop should appear at the end of the curve. Every step is a valid chopping (Shasha's Lemma 2). Code: `coarsening_chain` in `runtime/payment.py`; `python payment.py --plan --coarsen` prints it |
| R11 | `pa6` stays one operation | `c_ytd_payment += amount` and `c_payment_cnt += 1` are one operation, separate from `pa5` (`c_balance`) | TPC-C updates both in a single UPDATE on the customer row; splitting them would model something the workload doesn't do and add a round trip that exists only on paper. `c_balance` is split off only because it is displayed and therefore not commutative (F8) |
| R12 | Spec-conformant Payment inputs (**implemented**; before the server campaign) | NURand customer selection (clauses 2.1.6, 4.3.2.3, with the spec's last-name syllables), 15% remote customers, 60% lookups by last name. Every Payment gets a customer read `pc` of static attributes (`c_last`, `c_first`, `c_id`): a predicate read over the customers of a district for by-name (60%), a key read for by-id (40%). The read is unconditional because the spec displays the customer's name and address in both cases (clause 2.5.3.3). So every Payment has the same pieces and only the SQL differs, which keeps the chopped arms at a fixed piece count and the lock-hold measurement from mixing two shapes. `pc` takes no lock (F6, since Oct 14; it took `FOR KEY SHARE` before). **Implementation requirement:** the runner must carry the customer id resolved by `pc` into `pa5`, `pa6` and `pa7` (via the values passed between pieces, as `w_name`/`d_name` are today). Those statements must use that id, not look the customer up again, otherwise they perform a read the analysis doesn't model and the executed pieces stop matching `chop.py` | Checked with `chop.py`: `pc` is conflict-free in the full mix and in Payment only, under both triggers. B-inc becomes `{pa2} {pa3} {pa4} {pc} {pa5 pa7} {pa6}` (6 pieces), B-rec `{pa2} {pa4} {pc} {pa3 pa5 pa7} {pa6}` (5); the contended pieces are unchanged and `pc` runs before them (`pa5`, `pa6`, `pa7` use it). It costs both chopped arms the same extra piece, so the within-trigger gains stay comparable; and it is another instance of a conflict-free piece that adds cost without benefit. **Locking (since Oct 14, F6):** no lock: the read columns are never written, and customers are never inserted or deleted, so the matched set cannot change. (Before: `FOR KEY SHARE`, chosen over `FOR SHARE` because `FOR SHARE` conflicts at row level with other Payments' `pa5`/`pa6` updates.) **F6 sentence to extend:** two range reads now (all districts of a warehouse; the customers with one last name in a district), both over rows never inserted or deleted, with read columns never written. **Implementation (Oct 7):** `payment_params`, `nurand`, `last_name` in `runtime/payment.py` and `last_name`, `nurand`, `populate` in `schema.sql` follow py-tpcc (`util/rand.py`, `util/nurand.py`): same formula, syllables, load rule (customers 1–1000 of each district get `last_name(c_id−1)`, the rest NURand(255, 0, 999)), middle match at position ⌈n/2⌉, and constants C_LOAD = 157, C_RUN = 223, C_ID = 259, whose last-name delta satisfies clause 2.1.6.1. Index `customer_name` on (w, d, c_last, c_first) for the by-name lookup. Checked: 60% by name, 15% remote, every name in every district, 3 matches per name on average. NURand makes customer rows skewed (the most frequent id gets about 2% of by-id lookups), so the customer row now carries some real contention, as in the spec. The coarsening chain (R10) includes `pc` with the other conflict-free reads |
| R13 | Full mix: inserts, deletes and searches | Order, NewOrder and OrderLine rows are inserted (NewOrder) and deleted (Delivery) while Delivery and OrderStatus search them. The analysis models this with row-set cells (`o_row`, `no_row`, `ol_row`). At runtime each such cell gets one lock per district: a piece whose ops write the cell takes it exclusively, a piece whose ops only read it takes it shared. Taken at the start of the piece, in a fixed table order (orders, new_order, order_line), in the same call as the piece's first statement; Postgres advisory transaction locks, held to commit. `python mix.py --plan` prints them per piece | Row locks alone don't stop an insert from entering a search that is still running (phantoms), and Postgres has no predicate locks under 2PL. Every such search in TPC-C stays within one district, so a district-level lock is a correct predicate lock, and it is finer than the analysis (which ignores tuple identity) only in that it separates districts, which never share these rows. The fixed order prevents deadlocks between these locks. **Alignment with F9:** the analysis models these searches and inserts as accesses to one row-set cell per relation (F9), and with tuple identity ignored (F3) every search conflicts with every insert of that relation. Two separate facts make the runtime consistent with that: (1) the analysis is conservative, since its conflicts include every real one, so the chopping it computes is safe; (2) the district locks are a correct predicate lock, since every TPC-C search stays within one district. That the runtime locks more finely than the analysis is not by itself what makes it safe; (2) is. History's row-set cell gets no lock: nothing searches History, so inserts into it cannot invalidate a read (as in Payment only). **F6 sentence to extend:** 2PL on rows plus these district locks |
| R14 | District split vertically | `d_ytd` lives in its own table `district_ytd`; `district` keeps the static columns and `d_next_o_id`. Used by both workloads. **Quantified, not only argued:** `join_district()` restores the stock layout (`d_ytd` back in `district`, `district_ytd` a view on it, so every statement stays the same but locks the shared row), selected with `sweep.py --district joined`; every row records `district_layout`. Server stage `layout`: 1 warehouse, 32 clients, all four arms, both layouts, both workloads, back to back. **Results sentence:** report the difference (gain per trigger and where the clients wait, R18) between the layouts | Postgres locks whole rows. In one row, Payment's `d_ytd` update (and B-rec's read of all `d_ytd`) waits for NewOrder's long first piece, which updates `d_next_o_id`; with the pre-lock rule (R3) Payment holds the warehouse lock while it waits. The analysis treats them as separate cells, so that wait comes from row-level locking (R4), on exactly the lock the experiment measures. But the split also removes a wait that exists in the stock schema, so the result is partly conditioned on this choice; hence the `layout` stage. **Diagnosis (Oct 7, local, laptop in use; 1 warehouse, 32 clients, 2 reps; blocking chains of Payments waiting in their CPR call followed to the root):** in the mix with the stock layout the root is NewOrder in 44–75% of the samples (never with the split): a NewOrder holds the district row through its long first piece, Payment needs that row for `d_ytd` while already holding the warehouse lock (R3), so all Payments of the warehouse queue behind one NewOrder. Warehouse-lock waits rise from 55 to 220 ms (B-inc unchopped), 0.3 to 244 ms (B-inc chopped), 46 to 530 ms (B-rec unchopped, whose trigger also share-locks all ten district rows). Unchopped slows too because it also updates `d_ytd` under the warehouse lock. So the cause is the predicted `d_ytd`/`d_next_o_id` row contention; the split removes that and nothing else. Its size is amplified by the pre-lock order: a real trigger would take the warehouse lock after the district row and not hold it while waiting. Multixacts (combined share-lock records) are not the cause: about 4.6 vs. 4.8 per Payment in both layouts, from the warehouse and customer rows. In Payment only the stock layout was 6–42% slower within each rep, but with the same blocking chains and no new blocker; laptop noise (identical settings differed up to 2× between reps) prevents a conclusion, which the `layout` stage's 10 reps on the server will give. **For the paper (setup, next to the split; in this order):** (1) the split makes Postgres' row locks match the analysis' cells (`d_ytd` vs. `d_next_o_id`); (2) it also neutralizes a cost of the pre-lock rule (R3): with the split, only Payments ever lock `district_ytd`, so holding the warehouse lock while waiting for it adds nothing, whereas with the stock layout the rule makes Payment hold the warehouse lock while queuing behind NewOrder's district row, which a trigger taking its lock inside the statement would not do. That is a limitation of the harness, not of chopping; state it as such, with the `layout` stage's numbers, so the split is not read as hiding the pre-lock rule. **Spec:** clause 1.5.2 ("in the case of a vertically partitioned table, a row must exist in all the partitions") and clause 1.6 ("An implementation which uses vertical and/or horizontal partitioning must meet the requirements for transparent data access") permit vertical partitioning. Clause 1.6.1 also requires the application to use only the nine table names; our runner addresses `district_ytd` directly. That changes nothing about locking and goes into the one setup statement of R19 |
| R15 | One statement where the spec has one | Ops that the spec performs as one SQL statement on one row run as that statement when they land in the same piece: NewOrder's stock update of one item (`no8`, `no9`, `no10`), Delivery's customer update (`de6`, `de7`), Payment's customer update (`pa5`, `pa6`). In different pieces they run separately. Only the unchopped and coarsened Payment arms change (`pa5`+`pa6` in one statement) | Order within a piece doesn't affect the analysis, so this changes no chopping; it only removes round trips the spec doesn't have (as R11 argues for `pa6`). ## Proposition 1

At most one conflicting piece per template. Every conflicting operation lies in the conflict component of the unchopped second instance.

**Assumptions:**
- (a) the template can run concurrently with itself,
- (b) conservative variable equality (F3),
- (c) whether two operations conflict depends only on their access patterns: kind, cells and commutativity flag.

**Limitations** (to be named in the paper; future work: parameter constraints such as warehouse partitioning, ICDT 2022 functional constraints):
- self-concurrency (a),
- conservative variable equality (b).

Consequence: commutativity does not break Proposition 1; it changes which operations are conflict-free. A commutative increment is free only on a cell that no other template reads or overwrites non-commutatively.

## Metric

Reported per template and configuration (`metrics`, `free_increments`):

| Column | Definition | Counts triggered ops? |
|---|---|---|
| free hot increments | commutative updates outside the contended piece: locks that chopping releases early | **yes** |
| free reads | reads outside the contended piece: no lock benefit, reported for completeness | no |
| \|contended piece\| | operations in the contended piece; a change marks a merge (`*`) | no |
| triggered ops in the contended piece (optional, `chop.py -t`) | extra work CPRs add without merging anything | only triggered |

**Markers:**
- `*` merge: the contended piece differs from its reference (`none`, or `X-templates`),
- `†` a CPR blocked a rollback hoist (I7).

**Footnote:** the free hot increments that changed against `none`, named and ordered by rows per warehouse, hottest first (`TPCC_ROWS`). Templates-only runs are skipped.
